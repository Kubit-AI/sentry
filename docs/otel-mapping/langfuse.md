# Langfuse OpenTelemetry Mapping and Ingestion Heuristics

Langfuse trace/observation partitioning, sequential fallback chains, and metadata scoping rules.

See also: [`README.md`](README.md) for the OTel GenAI baseline conventions.

---

Langfuse is engineered as a highly scalable OTLP backend designed to ingest traces from heterogeneous sources, automatically normalizing disparate observability attributes into its unified, hierarchical data model. Langfuse processes both standard OTel attributes and its custom `langfuse.*` namespace, prioritizing explicit Langfuse directives to allow developers to override default OTel mappings when higher precision or custom filtering is required.

The translation hierarchy in Langfuse strictly partitions data between trace-level metadata and observation-level (span) metadata. At the trace level, the `langfuse.trace.name` attribute directly dictates the trace title, superseding the default OTel root span name, which is often generated generically by auto-instrumentation libraries. User session continuity, a critical feature for tracking multi-turn chat applications, is maintained by translating `langfuse.session.id` or the standard OpenTelemetry `session.id` resource attribute into Langfuse's native session tracking database.

At the individual observation level, the mapping logic implements sequential fallback chains. The standard `gen_ai.operation.name` is translated into the Langfuse `type` field, categorizing the execution strictly as a span, generation, or event. If an OTel span arrives lacking an explicit `gen_ai.operation.name` but contains a `gen_ai.request.model`, `llm.model_name`, or `model` attribute, Langfuse's ingestion engine leverages a heuristic to default the observation type to `generation`.

Payload mapping in Langfuse is designed to support multiple legacy instrumentation frameworks concurrently. For input parameters, Langfuse checks for `langfuse.observation.input`, falling back sequentially to `gen_ai.prompt`, then to `input.value` (specifically to support traces generated by the OpenInference standard), and finally to `mlflow.spanInputs`. A parallel fallback chain exists for generative outputs, scanning from `langfuse.observation.output` down to `gen_ai.completion` and `output.value`. To ensure precise trace correlation, Langfuse requires that certain trace-level attributes (such as `userId` and `tags`) be propagated to every span within the trace hierarchy using OpenTelemetry Baggage, as relying solely on root span attributes can lead to orphaned observations during aggressive span sampling.

| Langfuse Proprietary Attribute | OTel GenAI / Standard Equivalent | Langfuse Internal Mapping Target |
| :---- | :---- | :---- |
| `langfuse.observation.type` | `gen_ai.operation.name` | Observation type (`span`, `generation`, `event`). |
| `langfuse.trace.name` | Span Name of the Root Span | Trace name. |
| `langfuse.session.id` | `session.id` | Trace `sessionId`. |
| `langfuse.observation.input` | `gen_ai.prompt` / `input.value` | Observation input. |
| `langfuse.observation.output` | `gen_ai.completion` / `output.value` | Observation output. |
| `langfuse.observation.model.name` | `gen_ai.request.model` / `llm.model_name` | Observation model. |
| `langfuse.observation.usage_details.input` | `gen_ai.usage.input_tokens` | Observation usage (Prompt Tokens). |
| `langfuse.observation.usage_details.output` | `gen_ai.usage.output_tokens` | Observation usage (Completion Tokens). |
| `langfuse.observation.cost_details.total` | `gen_ai.usage.cost` (Custom) | Observation cost (Mapped to the `total` key). |
| `langfuse.trace.metadata.*` | Generic OTel Attributes | Filterable first-level metadata keys. |

To prevent metadata pollution and protect database query performance, Langfuse strictly partitions attributes. Attributes explicitly prefixed with `langfuse.trace.metadata.*` or `langfuse.observation.metadata.*` are mapped to first-level, filterable metadata keys. Conversely, unmapped generic OTel attributes (such as `http.method` or `net.peer.ip`) are automatically nested within a non-filterable `metadata.attributes` JSON object, preserving the diagnostic data for manual debugging without overwhelming the index. Furthermore, Langfuse implements a default export filter in its SDKs, ensuring that only spans generated by the `langfuse-sdk`, spans containing `gen_ai.*` attributes, or spans from explicitly whitelisted instrumentation scopes are exported, preventing traditional APM spans from cluttering the LLM observability dashboard.

## LangChain-via-Langfuse quirks

The Langfuse Python SDK (`langfuse>=4.x`, scope `langfuse-sdk/4.*`) and the Langfuse JS SDK (`@langfuse/otel>=5.x`, scope `langfuse-sdk/5.*`) ship a LangChain callback handler that wraps every LangChain runnable into a Langfuse observation. The two callbacks emit the same logical events but serialize them with subtly different shapes — enough that a transformer that only handles one SDK will break when the other appears. The kubit-otel langfuse adapter at [`frameworks/langfuse.{ts,py}`](../../nodejs-sdk/src/transformer/frameworks/langfuse.ts) reconciles both. The notes below are the divergences encountered in real LangGraph + ChatAnthropic traces and how the adapter handles each.

### Observation-type divergence: `span` vs `chain`

For LangChain wrapper observations (LangGraph root, the `tools` chain, `model_request`, `RunnableLambda`, `__start__`), the JS SDK emits `langfuse.observation.type = "span"` while the PY SDK emits `"chain"` for the same logical operation. The adapter folds JS `span` to canonical `CHAIN` whenever `langfuse.observation.metadata.ls_integration` starts with `langchain` so cross-SDK observation types stay aligned.

### Tool message shape divergence

The two callbacks serialize a LangChain `ToolMessage` differently:

| SDK | Wire shape on `langfuse.observation.output` |
| :---- | :---- |
| PY | Plain `BaseMessage.dict()` — `{"content":"85.0","type":"tool","name":"add","tool_call_id":"toolu_…","status":"success"}`. No `lc:1, type:"constructor"` envelope, no `role` field. |
| JS | LangChain Serializable envelope — `{"lc":1,"type":"constructor","id":["langchain_core","messages","ToolMessage"],"kwargs":{"name":"add","tool_call_id":"toolu_…","content":"85","status":"success"}}`. |

The shared `langchainEnvelopeToCanonical` helper recognizes both shapes (the plain-dict path was added so PY blobs route through the same translator as JS Serializables). Both produce the canonical `{role:"tool", name, parts:[{type:"tool_call_response", id, response}]}` shape.

### Tool-name-as-role on JS tool results

When the JS callback projects a tool result message *into the parent transcript* (e.g. inside `langfuse.observation.output` of a chain or root span), it uses the **tool name** as the role with no `tool_call_id` linkage:

```json
{"content": "85", "additional_kwargs": {}, "role": "add"}
```

The adapter rewrites any non-canonical string role to `role:"tool"`, lifting the matching `tool_call_id` from a same-array assistant `tool_call` part when present. Standalone tool-result spans (e.g. the JS `tools` CHAIN observation, which only carries the result message) get the rewrite without the id linkage. PY does not need this path — its plain-dict shape already carries `type:"tool"` + `tool_call_id`.

### Tool definitions

The PY callback injects each tool definition as a phantom `{role:"tool", content:{name, input_schema, description}}` entry inside `langfuse.observation.input`, sitting alongside the actual user/system messages. These aren't chat turns — the adapter strips them from `input_messages` and surfaces them via the top-level `tool_definitions` field instead.

The JS callback **does not emit tool definitions at all** — they're absent from every attribute on every span. This is an upstream gap (`langfuse-js` doesn't carry them through), not a transformer fix.

### Args serialization: `repr(dict)` vs `JSON.stringify`

For TOOL-typed observations, the args appear under `langfuse.observation.input`:

| SDK | Wire shape |
| :---- | :---- |
| PY | `"{'a': 47, 'b': 38}"` — `repr(dict)` output: single-quoted, invalid JSON. |
| JS | `'{"a":47,"b":38}'` — valid JSON. |

The PY langfuse adapter's TOOL-span synthesizer (see below) parses args via `safe_json_parse` first and falls back to `ast.literal_eval` to recover the dict. JS sees valid JSON and parses normally. Both end up with parsed-dict `arguments` on the synthesized canonical `tool_call` part.

### TOOL-span canonical synthesis

A bare `langfuse.observation.type = "tool"` span carries the tool args as `langfuse.observation.input` and the tool result as `langfuse.observation.output` — neither is shaped like a chat turn. The default `blobToMessages` flow would text-wrap the args as a fake `role:"user"` message. The adapter detects TOOL spans and synthesizes a canonical request/response pair instead:

- `input_messages` → `[{role:"assistant", parts:[{type:"tool_call", name, arguments, id}]}]`
- `output_messages` → `[{role:"tool", name, parts:[{type:"tool_call_response", response, id}]}]`

Tool name and `tool_call_id` are lifted from the normalized output's `tool_call_response.id`, so the synthesized input shares the same id the parent generation emitted. When the output envelope can't be normalized (e.g. raw-string output), input synthesis is skipped (no recoverable name) and output gets a fallback wrap with no id linkage. This mirrors the openinference adapter's `synthesizeToolSpanMessages` pattern.

### Metadata aliases on LangChain observations

The PY and JS callbacks both tag LangChain observations with provider/model metadata under `langfuse.observation.metadata.ls_*`. The adapter promotes these to first-class fields on the canonical record:

| Langfuse metadata key | Canonical Kubit field |
| :---- | :---- |
| `langfuse.observation.metadata.ls_provider` | `provider` |
| `langfuse.observation.metadata.ls_model_name` | `provided_model_name` |
| `langfuse.observation.metadata.ls_integration` | (used as discriminator for span→CHAIN folding; surfaced in `metadata`) |

### Known open gaps

- **JS tool definitions** (above): upstream `langfuse-js` does not emit them; needs an upstream feature request to resolve.
- **CHAIN spans wrapping LangGraph `Command` envelopes**: JS `model_request`, PY `model`/`tools` CHAIN observations carry outputs of the shape `{output:[{lg_name:"Command",update:{messages:[<AIMessage>]},goto:[]}]}`. The adapter currently text-wraps the entire envelope; the inner `update.messages` is recoverable but not yet unwrapped.
- **JS `RunnableLambda` LangGraph control envelopes** (`__end__`, `Send`): similar — text-wrapped today, may be intentional since they aren't chat content.
