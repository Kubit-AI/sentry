# Mastra (`mastra.*` namespace)

Mastra's `mastra.*` namespace, per-span-type input/output keys, and the OTel GenAI overlap on `MODEL_GENERATION` spans.

See also: [`README.md`](README.md) for the OTel GenAI baseline conventions.

---

Mastra is a TypeScript framework for building agentic applications: workflows, agents, RAG, tool calls, MCP, and a built-in evaluation harness. Mastra's tracing model assigns every operation a `SpanType` discriminator (`AGENT_RUN`, `WORKFLOW_RUN`, `MODEL_GENERATION`, `MODEL_STEP`, `MODEL_CHUNK`, `TOOL_CALL`, `MCP_TOOL_CALL`, `PROCESSOR_RUN`, plus `WORKFLOW_STEP` / `WORKFLOW_CONDITIONAL[_EVAL]` / `WORKFLOW_PARALLEL` / `WORKFLOW_LOOP` / `WORKFLOW_SLEEP` / `WORKFLOW_WAIT_EVENT`, and a generic `GENERIC` catch-all). Each `SpanType` is paired with a typed attribute interface (`AgentRunAttributes`, `WorkflowRunAttributes`, `ModelGenerationAttributes`, `ToolCallAttributes`, `ProcessorRunAttributes`, …) describing the per-type payload that the framework attaches to the span. Mastra ships several exporters that translate this internal model to OTel attributes: `@mastra/otel-exporter` aligned with OTel GenAI v1.38.0 semconv, plus targeted exporters for Datadog, Sentry, Langfuse, Arize, Braintrust, Laminar, and PostHog. This adapter targets the underlying `mastra.*` attribute namespace itself — the same shape every Mastra-owned tracer produces, regardless of which exporter is wired downstream. Apps shipping Mastra tracing into Kubit have been observed using the resource/scope name `@mastra/kubit` for an in-tree emitter that projects these attributes directly into the kubit-otel pipeline; the broader `@mastra/*` scope-prefix in `KNOWN_LLM_INSTRUMENTATION_SCOPE_PREFIXES` covers that case alongside the published `@mastra/core` and `@mastra/otel-exporter` packages.

Mastra writes OTel GenAI standard attributes wherever a Mastra concept maps cleanly to the spec — `gen_ai.operation.name`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, `gen_ai.agent.id`, `gen_ai.agent.name`, `gen_ai.tool.definitions`, `session.id`, `user.id`. On `MODEL_GENERATION` spans these standard keys carry the entire payload, so no Mastra-specific projection is required and the existing `otel_genai` adapter handles them unchanged. For every other span type, the Mastra-specific payload lives under per-span-type keys in the `mastra.*` namespace, structured as `mastra.<lowercase_span_type>.input` / `mastra.<lowercase_span_type>.output`. These are JSON-encoded blobs because OTel attribute typing forbids nested object literals — the wire encoding is always a string, decoded by the receiver.

The discriminator that ties the namespace together is `mastra.span.type`, set on every Mastra span to the lowercase form of the framework's `SpanType` enum (e.g., `agent_run`, `workflow_run`, `model_step`, `tool_call`). The Kubit transformer's `mastra` adapter dispatches its `normalize_messages` / `normalizeMessages` hook on this discriminator. `gen_ai.operation.name` mirrors `mastra.span.type` on most spans (e.g., both equal `invoke_agent` on root agent spans), so observation-type resolution flows through the existing `otel_genai` discriminator — no Mastra-specific override is required, and the saved `uppercase_unknown_op_names_verbatim` convention (`agent_run` → `AGENT_RUN`, `processor_run` → `PROCESSOR_RUN`, …) applies. Note Mastra's own enum value `INVOKE_AGENT` is preserved verbatim because `gen_ai.operation.name=invoke_agent` is the OTel GenAI standard agent-invocation operation.

Two attribute classes complicate the mapping. The first is the model-step debug bundle: `mastra.metadata.body` (the raw provider HTTP response, often multi-KB), `mastra.metadata.headers` (provider response headers including `server-timing`), and `mastra.metadata.modelMetadata` (a small JSON blob `{modelId, modelVersion, modelProvider}` describing the resolved model). Only `modelMetadata` is recovered into canonical fields — `resolve_provider` / `resolve_provided_model` / `enrich_metadata` parse it to fill `provider`, `provided_model_name`, and a structured `mastra_modelMetadata` metadata key on `MODEL_STEP` spans (which carry no `gen_ai.*` model alias of their own). The raw `body` and `headers` blobs stay in `attributes.span` rather than being hoisted into the metadata bag — surfacing a multi-KB response as first-class metadata creates ergonomic and sensitivity issues that aren't worth solving without a per-tenant policy. The second is the run-context trio: `mastra.metadata.runId`, `mastra.metadata.orgId`, `mastra.metadata.workspaceId`. These are stable per-run identifiers attached to every span; `enrich_metadata` hoists them into the metadata bag as flat `runId` / `orgId` / `workspaceId` keys.

`MODEL_CHUNK` spans require special handling. Mastra emits one per streamed token-chunk, and the payload is always `mastra.model_chunk.output: "{}"` — pure stream-coordination data with no LLM content. Mastra's own Sentry exporter skips them entirely to keep the trace tree readable; the Datadog exporter buckets them under the generic `task` span kind. The Kubit transformer follows the Sentry approach: `is_mastra_internal_span` / `isMastraInternalSpan` flags any span with `mastra.span.type=model_chunk` and the default `is_default_export_span` predicate drops them before they reach the transformer, sibling to the existing LangGraph-internal-span filter for `ChannelWrite<...>` / `__start__` / `__end__` Pregel coordination spans. `MODEL_STEP` is intentionally **not** filtered — even though it overlaps a sibling `MODEL_GENERATION` span in the same stream, it carries the raw HTTP response body / headers and the resolved model metadata that aren't visible elsewhere, and its input/output canonical projection is useful for debugging.

`mastra.completion_start_time` (an ISO-8601 millisecond timestamp set on streaming `MODEL_GENERATION` spans) is the first-chunk wall-clock time, mirroring Langfuse's `langfuse.observation.completion_start_time` semantics. The adapter exports it as `COMPLETION_START_ATTRS = ("mastra.completion_start_time",)`; `core.py` / `core.ts` merges it with Langfuse's tuple and consults the merged chain to populate the canonical `completion_start_time` field plus the third-tier `time_to_first_token` derivation (`completion_start_time − span.start_time`, ms-rounded, clamped to non-negative). Langfuse priority is preserved by ordering its tuple first, so a span carrying both keys still resolves to the Langfuse value.

| Mastra Attribute | OTel GenAI Standard | Adapter Routing |
| :---- | :---- | :---- |
| `mastra.span.type` | (none — vendor discriminator) | Drives `normalizeMessages` dispatch; `gen_ai.operation.name` carries the matching value for observation-type resolution. |
| `mastra.agent_run.input` (string) | (none — under `gen_ai.system_instructions`+events) | Projected as a single user-role text message. |
| `mastra.agent_run.output` (`{text, object?, files?}`) | (none) | `text` → assistant text part; falls back to stringified `object` when `text` is empty. |
| `mastra.processor_run.input` / `.output` (`{phase, messageList: {messages, systemMessages?}}`) | (none) | `messageList.messages` runs through the OpenAI-shape coercer; `systemMessages` are prepended as system-role messages. |
| `mastra.model_step.input` (`[{role, parts:[{text}]}]`, Gemini shape) | `gen_ai.input.messages` | Gemini-shape parts (`{text}` without `type`) are projected to canonical `{type:"text", content}`. |
| `mastra.model_step.output` (`{text, toolCalls?, object?}`) | `gen_ai.output.messages` | Assistant message: text part + tool-call request parts (mirrors `otelGenai`'s `mergeToolCallsIntoOutput`). |
| `mastra.tool_call.toolId` / `mastra.mcp_tool_call.toolId` | `gen_ai.tool.name` | Routed via `TOOL_NAME_ATTRS`; populates the canonical `tool_name` field. |
| `mastra.tool_call.input` / `.output` | `gen_ai.tool.input` / `gen_ai.tool.output` | Built into `tool_call` / `tool_call_response` parts that share the `toolCallId`. |
| `mastra.workflow_*.input` / `.output` | (none) | Best-effort coercion: known message arrays go through `coerceToMessages`; arbitrary JSON is wrapped in a single user/assistant text message. |
| `mastra.generic.input` / `.output` | (none) | Same best-effort path as `mastra.workflow_*`. |
| `mastra.metadata.runId` / `orgId` / `workspaceId` | (none) | Hoisted into the canonical `metadata` bag as flat `runId` / `orgId` / `workspaceId` keys. |
| `mastra.metadata.modelMetadata` (`{modelId, modelVersion, modelProvider}`) | (none) | Parsed; `modelProvider` → `provider`; `modelId` → `provided_model_name` (fallback for `MODEL_STEP`); whole blob → `metadata.mastra_modelMetadata`. |
| `mastra.metadata.body` / `mastra.metadata.headers` | (none) | Left in raw `attributes.span`. Not hoisted (size + sensitivity). |
| `mastra.completion_start_time` | (none — ISO timestamp form of TTFT) | Merged with `langfuse.observation.completion_start_time` in core; powers `completion_start_time` field + third-tier TTFT derivation. |
| `gen_ai.input.messages` / `gen_ai.output.messages` (on `MODEL_GENERATION`) | `gen_ai.input.messages` / `gen_ai.output.messages` | Routed through the existing `otel_genai` adapter unchanged. |
| `gen_ai.operation.name` | `gen_ai.operation.name` | Drives observation-type via `otel_genai.resolve_observation_type` (uppercase verbatim). |
| `gen_ai.system_instructions` | `gen_ai.system_instructions` | Injected as a leading system message by core's `system_instructions_injection` pass. |

Cross-SDK parity is mandatory: every alias and hook in `nodejs-sdk/src/transformer/frameworks/mastra.ts` must be mirrored byte-for-byte in `python-sdk/kubit_otel/transformer/frameworks/mastra.py`, including the Gemini-shape projector for `MODEL_STEP` input. Filter parity is also required: `is_mastra_internal_span` / `isMastraInternalSpan` plus the `@mastra` scope-prefix entry in `KNOWN_LLM_INSTRUMENTATION_SCOPE_PREFIXES` must match in both SDKs. CI has no parity check — the mapping table above plus the broad-test fixtures (`tests/transformer.broad.test.ts`'s "Mastra schema" and `tests/test_transformer_broad.py`'s `TestMastraSchema`) are the contract.
